On some connections the first upload of a session failed, and the second always worked.
From 1.4.2 the app does the second attempt for you, and when an upload does fail it says
why.

## Fixed

### An upload that times out on Steam's side starts again by itself

- Sometimes Steam's upload server does not answer the first request of a build, usually
  on the first upload after a pause. `steamcmd` then stops with
  `ERROR! Timeout uploading manifest`. Pressing *Upload build* again worked every time this
  has been seen.
- The app now does that for you. It waits ten seconds and runs the same upload again,
  once. The log shows a yellow line saying so, the progress bar starts over, and when the
  build goes through the status line says on which attempt it did.
- Retrying is safe. Steam creates a build only after every depot is in, so a failed
  attempt leaves nothing behind, and depots that did get uploaded are reused rather than
  sent twice.
- Only this failure is retried. A wrong password, a rejected depot or a broken script
  would fail the same way again, so they are reported at once, as before.
- If the second attempt times out too, the message says so and that nothing was created
  on Steam. Press *Upload build* to try again, and check the connection if it keeps
  happening.

### Build errors show their real reason

- `steamcmd` puts a timestamp in front of the errors it raises while building. The app did
  not recognise those lines as errors. Worse, `Build for depot … failed : Failure` was read
  as a failed login, so a failed upload was reported as just **Failure**, in red, as if
  the password were wrong.
- Errors raised while building are now recognised. The reason shown is `steamcmd`'s own,
  for example `ERROR! Timeout uploading manifest (size 58468)`.

## Known issues

- **The automatic retry has been checked against real logs, not against a live failure.**
  The lines it reacts to were taken from `steamcmd`'s log of two uploads that failed this
  way, and the test suite feeds them through the same code. But no upload has timed out
  since the change, so the retry itself has not yet been seen running.
- **The exported GitHub Actions workflow does not retry.** It runs `steamcmd` itself, so a
  timeout there still fails the job; run it again.
- **A project's own Web API key has still not been tried against Steam with keys from two
  different partners.** If a project's own key is not picked up, please open an issue.
- **The packages are not code-signed yet.** The first time, Windows SmartScreen shows
  "Windows protected your PC": choose *More info → Run anyway*. macOS refuses software from
  an unidentified developer: Control-click the package or the app and choose *Open*, or
  allow it under *System Settings → Privacy & Security*.
- **The macOS packages have not been tried on a real Mac yet.** If something does not work
  there, please open an issue with your macOS version and chip.
- **A portable copy's first update downloads the full package** (about 50 MB), because the
  portable archive does not include the package that updates are calculated from. Later
  updates, and every update of an installed copy, download only the differences.

## For contributors

- `SteamCmdOutputParser` matches failures against the message without `steamcmd`'s
  `[time]: ` build stamp. `IsTransientUploadFailure` names the one failure that is retried.
- `SteamCmdSession.UploadAttempts` (2) and `ShouldRetryUpload` hold the retry rule.
  `UploadOutcome.Attempts` says how many runs an upload took.
- The test suite is at 231 assertions.
